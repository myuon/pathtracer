# 計測 (bench)

等時間 / 等 spp のノイズを自動で測る。手で目視比較していた「◯◯を入れたら
何倍良くなったか」を数値で出すためのもの。

## 仕組み

- `?bench=1&...` でアプリを計測モードに入れる (`src/bench.ts`)。UI も rAF の
  可変ロジックも通さず、決めた設定で決めた予算ぶんだけ回し、累積バッファを
  HDR のまま `window.__bench` に置く
- `bench/run.mjs` が vite の dev server と Chrome を立ち上げ、設定ごとに
  ページを開いて結果を集め、参照画像との誤差を出す
- **1 回の計測につきページを 1 枚使い切る**。ガイド格子や光子の放出
  ヒストグラムといった「学習した状態」が前の計測から漏れない

## 使い方

参照画像を作る (バイアスのない PT + NEE + MIS で焼く。`bench/ref/` は git 管理外):

```sh
node bench/run.mjs ref --spp=32768 --sppf=32 --bounces=12 --w=320 --h=240
```

設定を比べる (等時間):

```sh
node bench/run.mjs run --scenes=cornell,glass --ms=10000 --bounces=12 \
  --config "base:guide=0" --config "guide:guide=1"
```

等 spp なら `--ms` の代わりに `--spp` を渡す。

## 出る数値

| 指標 | 意味 |
| --- | --- |
| `rmse` | 線形 HDR での二乗平均平方根誤差。明るい所に引きずられる |
| `relmse` | `(a-b)^2 / (b^2 + 0.01)` の平均。暗部を潰さない。**基本はこれを見る** |
| `aces` | ACES + ガンマを通してからの RMSE。見た目に近い |
| `trim` | 上位 1% の画素を落とした relMSE。**サンプラの比較はこれで見る** |
| `med` | 画素ごとの相対二乗誤差の中央値。典型的な画素がどれだけ合っているか |
| `eff` | `relmse x 秒`。小さいほど良い。**等時間の優劣はこれで見る** |

最後に、先頭に渡した `--config` を基準にした relMSE と効率の倍率が、
シーンごとと全シーンの幾何平均で出る。1 より大きいほど良い。

等時間 (`--ms`) で測るより、**等 spp (`--spp`) で測って `eff` を比べる方が
再現性が高い**。等時間だとフレーム数の刻みで結果が動くのに対し、等 spp なら
サンプル列が固定 seed で完全に決まるため。

## デノイザを測る

デノイザは present のフラグメントシェーダの中で効くので、累積バッファを
読むだけでは効果が測れない。`--present` を付けると、トーンマップと
デノイズを通した後の絵 (sRGB 8bit) も読み戻し、参照画像を同じトーンマップに
通したものとの RMSE (`ldr`、0〜255 スケール) を出す。

```sh
node bench/run.mjs run --scenes=cornell --spp=64 --present \
  --config "off:denoise=0" --config "on:denoise=1"
```

## 壊れている場所を探す

`--dump` を付けると各設定の HDR を `bench/out/<scene>_<config>.f32` に
落とす (画素あたり RGB の float32、そのまま `Float32Array` で読める)。
参照画像と割り算して粗いマス目に落とすだけで、誤差が「点で出ているのか
輪郭に沿って出ているのか」が一目で分かる。SPPM が別の面の光子まで
拾っていたバグは、誤差がジオメトリのシルエットをなぞっていたことから
見つけた。

## アプリ本体を通す煙テスト

`bench` は `main.ts` の rAF ループを丸ごと迂回しているので、そこでしか
出ない不具合は捕まらない。`bench/smoke.mjs` は実際のアプリを起動して
カメラ操作・全シーン切り替え・一時停止/再開まで通し、コンソールに
エラーが出ないことと spp が進むことを確かめる。

```sh
node bench/smoke.mjs      # または pnpm bench:smoke
```

シーン切り替えの後始末は `--config "...,before=<別のシーン>"` でも試せる。
先にそのシーンを描いてから本命へ切り替えるので、学習した分布や光子グリッドが
持ち越されていれば数値がずれる。

## 比較画像を作る

`bench/shot.mjs` はアプリを実際に起動して、同じ壁時計時間だけ回した絵を撮る。
`bench/compose.mjs` はそれをラベル付きで横に並べる。別の版と比べたいときは
`git worktree` でその版を用意して `--root` に渡す (`/tmp` は macOS だと
symlink で vite が解決に失敗するのでホーム以下に置くこと)。

```sh
git worktree add ~/pt-old main
ln -s "$PWD/node_modules" ~/pt-old/node_modules
node bench/shot.mjs --root=~/pt-old --out=/tmp/a --scenes=maze,ajar --ms=180000
node bench/shot.mjs --root=.       --out=/tmp/b --scenes=maze,ajar --ms=180000
node bench/compose.mjs --a=/tmp/a --b=/tmp/b --scenes=maze,ajar --out=/tmp/c.png
cwebp -lossless /tmp/c.png -o docs/xxx.webp
```

短い時間で撮ると「遅いが正しい」実装が不利に見える。実装の正しさを見たい
ときは十分に積んでから撮ること。

## 定数の突き合わせ

WGSL と TS の両方に同じ値を手で書いている定数がいくつかある
(`GRID_CAP` / `MAX_DEPOSITS` / `HIST_BINS` / `GUIDE_VOX` / `GUIDE_BINS` /
`VTX_SLOTS`)。ずれても何も言わずに壊れる (バッファの大きさや索引が狂う)
ので、触ったら必ず確かめること。

```sh
node bench/consts.mjs     # または pnpm bench:consts
```

`struct Uniforms` が `UNIFORM_SIZE` に収まっているかも同時に見る。
今ちょうど 336 バイト = 上限いっぱいなので、フィールドを足すときは
`UNIFORM_SIZE` も上げる必要がある。

## 落とし穴

- **参照画像と検証画像で乱数の塩を変えること** (`run` は自動で `salt=1`、
  `ref` は `salt=0`)。同じにすると、検証側の N 点が参照側の点列の先頭 N 点と
  そのまま一致し、誤差が打ち消し合って**実際より 1.7 倍も良く見える**。
  相対比較なら両方に同じ下駄が乗るので順位は変わらないが、絶対値は信用できない
- **計測のばらつきは 1 シーンあたり最大 6% ある**。同じ設定を別の乱数実現で
  2 回測って確かめた値なので、これより小さい差は読み取らないこと。
  全 12 シーンの幾何平均なら 0.3% まで落ちる
- **シェーダのコンパイル失敗は console.warning にしか出ない**。WebGPU は
  そのまま走り続けるので真っ黒な絵が「結果」として返る。`run.mjs` が
  検知して落とすようにしてあるが、数値だけ見て判断しないこと

## 注意

- **パストレースが収束しないシーンは別の推定量で焼く**。`REF_OVERRIDE` に
  書いてある。今のところ 2 つ:
  - `submerged` は SPPM。PT は平均輝度が 131072 spp でも伸び続けるのに対し、
    SPPM は 1024 spp で止まり、集光半径を 1/4 にしても動かない
  - `ajar` は VCM。PT は 131072 spp でも +1.1%/4 倍で伸び続けるが、VCM は
    増分が +1.77% → +0.24% → +0.17% と落ちて収束する
- **参照画像が収束していない場合がある**。`ref` は予算の 1/4 でも焼いて
  平均輝度の動きを見て、2% 以上動いていたら「未収束」と出す。出たシーンの
  数値は信用しないこと。
  この検査は `submerged` で実際に引っかかった。32768 spp の PT でも平均輝度が
  4 倍の予算ごとに +13% ずつ伸び続けていた (256 spp で 0.276 → 131072 spp でも
  収束しない)。小さな光源が波打つ水面の向こうにあるので、単方向のパストレースでは
  その経路をほとんど引けない。**この状況では「SPPM が正しく参照が誤り」**で、
  relMSE は SPPM が正しいことを罰してしまう。今は `REF_OVERRIDE` で
  SPPM から焼いていて、PT 7.79e-1 に対し SPPM 2.69e-3 と正しく出る
- **relMSE は少数の画素に支配されることがある**。veach は光沢板のシルエットに
  出る firefly 十数個で relMSE の 58% が決まり、素の relMSE では
  「QMC を切った方が 2 倍良い」という誤った結論になる。同じ比較を
  `trim` で見ると 1.09 倍、`med` で見ると **QMC 有りが 3.8 倍良い**
  (被写界深度のある spheres では 32 倍)。サンプラのように「大多数の画素を
  均す」施策は、必ず `trim` か `med` で判断すること
- **参照画像そのものが firefly を拾うことがある**ので、`ref` は既定で
  複数回まわして平均する (`--repeat`)。veach の参照は 1 回だと
  (85〜86, 107〜110) の数画素で 1.5 〜 1.9 倍明るく、それだけで画像全体の
  平均が 0.45% ずれていた (差の上位 5 画素で全体差の 215%)。6 回平均に
  すると絶対 relMSE が 1.46e-2 → 2.54e-3 まで下がる
- バイアスのある推定量 (SPPM) と無バイアスな推定量 (PT) を比べるときは
  relMSE だけで決めないこと。relMSE は暗部の相対誤差を強く見るので、
  ボケているが概ね正しい絵を過剰に罰する。ACES-RMSE も併せて見る
- `--w` `--h` `--bounces` を変えたら参照画像も作り直す (ファイル名に全部入る)
- `guide` はパストレース経路 (`trace()`) にしか効かない。`sppm=1` では
  `sppmMain` が走るので、`guide` を測るときは `sppm=0` にすること
